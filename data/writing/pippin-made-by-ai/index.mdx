[Pippin](https://th1nhng0.itch.io/pippin) is a short point-and-click game I made for thatgamejam #02. Nell inherits her grandmother's cabinet. It has five drawers, and each drawer holds a tiny living model of a place from Ida's life: a farm, a city block, a harbour, an island, a launch pad. A slider at the bottom of the screen moves the whole model through time. The puzzles are about doing the right thing at the right moment.

I did not write any of it. Claude Code wrote all the code, drafted the story and dialogue, and generated the voices, music and sounds through ElevenLabs. I directed it and reviewed what came back. The repo has 53 commits over five days, from November 1 to 5.

This post is mostly a look inside: what the AI actually built, and the tricks it used to make a game it can't see or play the way I do.

## Five drawers

Each chapter is one diorama, and each one covers a different span of time. The slider runs through a year on the farm, a decade on the city block, one night at the harbour, decades on the island, and the last six seconds before a launch.

## Every pixel is code

The first thing I wanted to know when I opened the repo was where the art came from. The answer is a few hundred lines of JavaScript that place colored points on an isometric grid, and a lot of scene files that call them.

The renderer keeps two buffers the size of the screen: one for color and one for depth. To draw a point in 3D space, it turns the point into a screen position and only writes it if nothing closer has been drawn there yet:

```js
export function dp(x, y, z, c) {
  const sx = x - y + ox, sy = ((x + y) >> 1) - z + oy;
  const i = sy * W + sx, d = x + y + z;
  if (d >= depth[i]) { depth[i] = d; fb[i] = c; }
}
```

In this isometric view, `x + y + z` is exactly how close a point is to the camera, so the depth test is one comparison. Buildings, roofs, trees and water are made from helpers on top of `dp`, like `box`, `roof`, `cyl` and `canopy`.

The farm is drawn into a 388 by 243 pixel buffer, then scaled up with sharp edges. That is why it looks like pixel art: it really is that many pixels.

The static parts of a scene are built once and stored as a flat list of points. The farm has 66,414 of them. Each frame, the game just copies those points into the buffers, then draws the things that move on top: people, smoke, birds, water. This is what drawing the farm's point list in order looks like, slowed way down:

The seasons work because every scene is a function of one number, the slider position from 0 to 1. On the farm, `p * 12` is the month. Tree colors, snow, the crop in the field and the color of the sky all read from it. Drag the slider and you are just calling the same drawing code with a different number.

## Doing something early changes later

The slider was the part of the game that changed the most. In the first version it was only a way to look for the answer: drag until a clickable thing shows up, then click it. A review on November 4 called that out, and the rework built the game around a new rule: what Nell does at one moment shows up in every later moment, and never in earlier ones.

The code for this is tiny:

```js
export const mark = (k, p = S.p) => { G.marks[k] = p; };
export const since = k => k in G.marks && S.p >= G.marks[k];
```

When Nell hangs a lit lantern in the orchard, the game calls `mark('smudge')` at that slider position. If that was before the April frost night, the blossom survives and the tree has apples in summer. If it was after, the frost already got them. Do it again at a different time and the mark moves, so a wrong choice can always be fixed by going back. Each chapter has at least one puzzle like this and one choice that costs something. Those rules are written down in the repo as design rules the AI has to follow.

## Hints that have to point somewhere

Point-and-click games are famous for getting players stuck. Pippin's Hint button opens in three steps: a nudge in words, then the room or the time to look at, then an arrow on the exact thing. Each step unlocks 45 seconds after the last one.

Every goal in the game is written as `goal(what, how, at)`. `what` is the objective on screen and never says how. `how` is the nudge. `at` names the things the arrow should point to. That last part is what keeps the hints honest, because a test can check it.

## A robot that plays the whole game

The AI can't sit and play the game like I do, so it wrote a player that does.

The intended solution for each chapter is a list of steps. Each step is a slider position, the name of a thing to click, and the item to use on it:

```js
const START = [[.02, 'Tobias Marsh'], [.92, 'Reeds in the pond'],
  [.92, 'Barn door', 'KEY'], [.92, 'Orchard ladder'], ...];
```

Playwright opens the game, and for every step it moves the slider, works out where that thing is on screen, and checks three things before clicking: the thing exists at that time, it is inside the screen, and a click at that pixel really hits it and not something drawn on top of it. After every step it opens the hint and fails if the hint points nowhere.

It plays all five chapters to both endings. It also plays the other branch of Chapter I's choice, and checks that the game can be played with only a keyboard. There are 59 tests, and the whole check (types, lint, build and tests) runs in about five seconds.

There is also a small test for the voices. Every voiced line is matched to its audio file by its exact text. If someone edits a line of dialogue and forgets to regenerate the voice, the test fails. With 279 voice clips, that would be easy to miss by hand.

## Seeing its own work

The AI also needs to see what it drew. The repo has a command that takes a screenshot of one chapter, one room, at one slider position:

```
CH=1 ROOM=barn P=.5 npm run shots
```

The project notes tell the agent to always narrow it down like this and only open that one image, so it doesn't fill its context with dozens of screenshots. A lot of the commit history is the AI fixing what it saw in those images: "Move the front floodlight mast off Ida's line at the gantry", "Prune the orchard and give the harbour boats real hulls", "Break the vertical curtains on the island's slopes".

It also wrote down what it couldn't check. The game audit says plainly that it did not hear the audio, and judged the sound mix only from the code. The to-do list says tests prove the game can be finished, not that it is fun, and that only people playing it can answer that.

## Notes for the agent

The file that holds all of this together is `CLAUDE.md`, the instructions the agent reads before it does anything. It has a table of which file to open for which kind of change, the coordinate system, the design rules, and writing rules for the dialogue, such as:

- Every clickable thing must do something. A thing that only makes a remark gets removed.
- No character says the solution. People state the problem, and the scene shows the way.
- Each character has their own way of talking, and no line ends with a moral.

Some rules are lessons from mistakes. One says flag names are shared across chapters, because Chapter III's first version reused a flag from Chapter I and broke the whole-game run. Another says agents working in parallel must each use their own port, since several chapters were reworked at the same time in separate worktrees.
